# Agent Loop

Единый порядок работы агентов. Файл байт в байт одинаков в `open-code-ai`, `php-eggheads`, `ai-proxy`, `eggheads-dictation`, `eggheads-voice-expert`, `eggheads-db` и `internal-services`: правка вносится сразу во все и подтверждается пин-тестом, чья команда названа в правилах проекта. Проектные команды проверок и гейты живут в правилах проекта.

```text
план -> реализация + самопроверка -> независимый QA -> исправление + самопроверка -> независимый QA -> ... -> pass
```

Автор работает в одном потоке и сдаёт законченный результат. QA каждый раз независим и проверяет всё заново от исходной задачи. Цикл заканчивается pass или остановкой по правилам ниже.

## Режимы

| Режим | Когда | Цикл |
|---|---|---|
| `direct` | Чтение, диагностика, механика без изменения поведения | Без QA |
| `light` | Любая реализация поведения; выбирается по умолчанию | Полный цикл |
| `critical` | Есть эффект из таблицы ниже | Полный цикл, QA усиленный, обязательные доказательства |

Режим называй одной строкой с причиной. Сомнение решай в пользу более строгого режима. Одна строка изменения поведения не требует `critical`, если эффекта из таблицы нет. Если в ходе `direct` меняется поведение, это уже `light`.

Если неизвестно, есть ли эффект, реализацию не начинай: назови недостающий источник и сделай ограниченный read-only шаг. До старта проверь, что новый субагент для QA доступен.

## Планирование

- Обычный план пишет автор и показывает пользователю. Если пользователь просит независимое ревью плана, его делает новый субагент.
- Показанный план реализуется после того, как пользователь его принял. «Делай и перепроверяй» — это весь цикл до pass.
- `full` планирование (`docs/agent-planning-loop.md`, в репозитории без этого файла — он же из `open-code-ai`, а если он недоступен, скажи об этом и остановись) запускается только по прямому слову пользователя в текущем диалоге. Агент может предложить его одной строкой для очень сложной задачи, но не включает сам.

## Автор

- Автор, обычно main, делает реализацию, все согласованные проверки и исправление причинного класса: перечисляет все ветки того же дефекта, закрывает их одной правкой и проверяет границы. Обычный отказ теста остаётся у него.
- Новый parser, protocol, state, journal, recovery или control layer: до кода назови существующий аналог, почему его мало и какой сложности это стоит.
- На QA идёт готовый проверенный кандидат. Известный отказ и незавершённая проверка закрываются до QA, а не передаются ему.
- Замечания QA исправляет автор одним проходом по всем находкам, сгруппированным по причине. Новый контекст для исправления не нужен.
- Отдельный исполнитель — решение о делегировании, а не режим: для независимых групп работ со своими файлами и своим worktree либо для задачи, которая иначе вытеснит контекст main. Исполнитель владеет стадией целиком и возвращает результат или настоящий блокер. Main не ведёт его по шагам.
- Пишет один поток. Параллельные писатели допустимы только в непересекающихся файлах.

## Независимый QA

- Каждый проход — новый субагент без истории автора. Роль не выполняет автор и не подменяет последовательным roleplay в том же контексте.
- На вход: исходная задача, принятый план, идентификатор кандидата (SHA коммита или хэш незакоммиченного diff), `Check Map`, заявленные режим и эффекты. Прошлые находки и выводы автора — как утверждения, а не как факт.
- Пока идёт проход, кандидат не меняется.
- QA сам заново выводит эффекты из diff. Заниженный режим — находка не ниже `major`.
- QA проверяет всё от исходной задачи, а не только прошлые замечания: корректность, покрытие плана, регрессии, тесты, правила проекта, лишний scope. Подсказка «посмотри, исправлено ли прошлое» запрещена.
- QA собирает все находки за один проход и может сам запускать проверки и живой прогон в разрешённых границах проекта.
- Находка содержит дефект, доказательство, последствие, серьёзность и проверку. Предпочтение без доказательства не блокирует.
- Серьёзность: `blocker` — работу нельзя принять или продолжать; `critical` — потеря данных, денег, безопасности; `major` — неверное поведение, нарушение задачи или правила, неполученное обязательное доказательство; `minor` — малый дефект без влияния на результат. `blocker`, `critical`, `major` останавливают pass.
- Pass действует только для проверенного кандидата: коммит с тем же содержимым его сохраняет. После него `minor` можно лишь назвать; любая правка означает новый проход QA.
- Спорную находку автор опровергает фактом, следующий QA видит спор. Если он не разрешается, решает пользователь.
- Промпт — `.ai-loop/prompts/qa-reviewer.md`, если он есть в репозитории.

## Остановка

- Лимит — 5 проходов QA на задачу, если пользователь не задал меньший бюджет. Продолжение требует точного нового лимита от пользователя в текущем диалоге. Счётчик веди в MR или файле плана, а без них называй в каждом отчёте пользователю: новый чат и сжатие контекста его не обнуляют.
- Автор сравнивает находки проходов. Та же находка или тот же механизм вернулись после исправления либо проход не дал движения: остановись, пересмотри подход, сообщи пользователю.
- После 10 проходов нужен другой подход.
- Новый субагент для QA недоступен: цикл не завершён, скажи об этом и остановись. Самопроверка QA не заменяет.
- Решение вне утверждённого scope, полномочий или продуктовых правил принадлежит пользователю.

## Critical

Эффект определяй по фактическому изменению, а не по словам в задаче, именам файлов или числу строк. Аддитивная миграция без риска блокировки и работа с уже выданным секретом через существующий защищённый путь эффектом не являются. Для каждого эффекта до QA нужно названное доказательство.

| Эффект | Доказательство |
|---|---|
| Семантика хранимых данных, миграция, backfill | `state-contract-proof` |
| Публичный API, внешний payload, webhook | `external-contract-proof` |
| Аутентификация, авторизация, изоляция, секреты, приватность | `authz-isolation-proof` |
| Биллинг, квоты, балансы, деньги | `accounting-proof` |
| Риск потери данных, денег или утечки | `destructive-operation-proof` |
| Выбор провайдера, failover, идентичность модели | `provider-routing-proof` |
| Топология, раскатка, владелец процесса | `runtime-ownership-proof` |
| Согласованное изменение нескольких сервисов | `cross-service-contract-proof` |
| Откат невозможен локально | `rollback-proof` |

В `critical` QA выполняет самая сильная доступная модель. Каждое доказательство — воспроизводимая команда или сценарий с актуальным результатом по правилу повтора ниже. Неполученное доказательство — не pass.

## Доказательства и отчёт

- `Check Map` — короткий список на входе QA: риск, команда или сценарий, актуальный результат.
- Проверки соразмерны риску: focused в ходе работы, полный обязательный набор проекта на готовом кандидате. После исправления повтори проверки, чьи файлы или поведение оно затронуло; остальные результаты остаются действительными, их актуальность оценивает QA.
- Объяснение субагента сверяй с его исходным ответом и trace, прежде чем действовать по нему.
- Ожиданием владеет инструмент: блокирующий или фоновый запуск и один итоговый результат. Лог без новой информации не читается.
- Пользователю в конце: что изменилось для продукта, чем проверено, сколько было проходов QA, что не проверено.
